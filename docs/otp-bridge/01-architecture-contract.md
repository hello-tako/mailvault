## Versioned contract

Browser POST `/api/shop/me/orders/:orderId/otp` accepts only `{allocationId}` in at most 1024 streamed bytes. Origin, URL origin, optional Fetch Metadata, existing secure session, proof younger than ten minutes, order ownership and the exact fulfilled allocation are checked before RPC. The final grant query also checks proof/session, current customer, payment, inventory, binding, expiry and grant version in the same SQL statement. It returns only `{ok,state,code,receivedAt}` or the specified generic error/pending response. Responses use private no-store and nosniff; existing account pages additionally disable Cloudflare CDN caching.

`MAILVAULT_OTP` binds service `mail-vault`, named export `CustomerOtpReader`. Only `validateAlias` and `lookupLoginOtp` are application RPC methods. Default fetch/email/queue/scheduled behavior is preserved. No owner credentials, inbox routes or cross-D1 reads are introduced.

Both sides use secret NAME `OTP_BRIDGE_RPC_HMAC_KEY` (no value is provisioned). HMAC-SHA256 covers the JSON array `["TUNG-OTP-BRIDGE",1,operation,aliasId,providerKey,grantId,notBefore,issuedAt,requestId]`. IDs, UTC millisecond timestamps, UUID nonce and lowercase 64-hex MAC are strictly checked. Maximum issue skew is 30 seconds. `crypto.subtle.verify` verifies the MAC; a globally unique D1 nonce reserves one use with 60-second retention and bounded pruning. Operation and every mapping/window field are signed. Customer input never chooses a remote alias or provider.

`validateAlias`: `{state:active|inactive|not_found|routing_unknown,aliasId}`. It requires ACTIVE alias, domain READY/READY/OURS, enabled compiled policy and a dedicated `routing_verified_at` proof within two hours. This proof is written only after bounded, complete delivery-path reads confirm active Email Routing, Cloudflare MX without a foreign MX conflict, no enabled ordinary Email Routing rule that can shadow the alias, and an enabled catch-all with exactly one `worker` action targeting MailVault on an active full zone. The ordinary rules endpoint is read with Cloudflare's documented `per_page=50`, at most 20 pages/1000 rules; missing/inconsistent pagination metadata, duplicate IDs, malformed actions/matchers, or incomplete pages fail closed. Discovery sync and provider mail do not create or refresh the proof. This separates non-secret provisioning readiness from provider-message classification: cold inventory aliases need no provider receipt in the previous 24 hours. The proof is a bounded routing observation, not a promise of future delivery; all actual code lookups still enforce exact sender and cryptographically verified aligned DKIM.

`lookupLoginOtp`: `{state:found,code,receivedAt,messageRef}` or `{state:pending|ambiguous|untrusted|unavailable}`. `messageRef` remains internal. MailVault independently clamps age to at most 120 seconds and rejects pre-entitlement/future messages. It queries exact alias, IN, COMMITTED, TRUSTED and existing visibility/tombstone/staging fences, newest first. A 21st sentinel row makes a 20-row scan fail ambiguous. Sender needs exact reviewed From AND allowlisted independently verified aligned DKIM. Full private parsed R2 text is read only to corroborate extraction and reject reset/recovery/financial/account-change purpose; max object 256 KiB, text 64 KiB. Existing `extractOtp` and shared schemas are reused. Competing distinct codes fail ambiguous. Final visible snapshot, age, alias and routing checks fence changes completed during R2 reads.

The real `muse` registry remains disabled, with empty sender/signer allowlists. Synthetic test policy exists only in test bundles. No sender address or provider behavior is guessed.
